## 2026-09-27 - UI audit pass on the Lovable frontend: three real defects, not doc-relevant but recorded for the next visual audit

Requested audit of the redesigned frontend (screenshots showing a
misaligned rider-row menu and a "New shipment" sheet that appeared to
jump). Found and fixed, all in `frontend/src/`:

- **`Modal` (`components/owner/OwnerLive.tsx`) never locked background
  scroll.** The backdrop is `position:fixed`, but the page behind it
  stayed scrollable, so a wheel/trackpad scroll while a sheet was open
  moved the list underneath — read as the sheet's own content jumping
  between renders. Added a scroll-lock `useEffect` (sets
  `document.body.style.overflow='hidden'` for the modal's lifetime).
- **`--popover` and `--destructive` were referenced throughout
  `components/ui/*.tsx` (13 shadcn primitives) and by `.pop-menu` /
  `.pop-menu .danger` in `styles.css`, but never declared anywhere in
  `:root` or the `@theme inline` block.** They silently resolved to
  transparent / unstyled, so the riders-page row menu had an invisible
  background (row content showed straight through the menu's own
  bounds) and both real "destructive" actions in the app — deactivate
  rider, delete a cancelled shipment — rendered with no distinguishing
  color at all. Declared both tokens (`--popover` aliased to `--card`;
  `--destructive` a new red, shadcn's default `oklch(0.577 0.245
  27.325)`) and wired their Tailwind `--color-*` aliases. Also widened
  `.pop-menu` to cover the full row it anchors to (was `min-width:180px`
  right-aligned, leaving part of the row it should cover visible beside
  it) by moving the `position:relative` anchor from just the kebab
  button to the whole card-header row.
- **`.agent-dock` (`RiderLive.tsx`'s bottom action bar) was
  `position:sticky`, which can render *above* its own natural flow
  position — not just prevent it scrolling away.** Once a shipment's
  History list plus the address/phone/scheduled cards ran taller than
  (viewport − header − dock − margin), the dock's natural static bottom
  edge fell below the sticky `bottom` line even at scroll position 0, so
  sticky pulled it upward to satisfy that constraint, painting over the
  last one or two timeline entries instead of pushing them below the
  fold. Removed `position:sticky` (now a plain in-flow block) — trades
  "always reachable without scrolling" for "never overlaps the content
  above it."
- Sidebar's "Your account" link (`components/DeliveryApp.tsx`) was
  labelled "Profile & sign out" but only navigated to `/owner/account`
  — it did not itself sign out. Added a separate one-tap sign-out icon
  button next to it (same `clearSession(); navigate({to:'/login'})`
  pattern already used on `OwnerAccountPage`/`AgentAccountPage`);
  relabelled the link "Profile & settings" since it no longer claims to
  do something it doesn't.
- Also found and fixed, unrelated to the UI: the register form labels
  `businessPhone` "optional" but `RegisterRequest.businessPhone` is
  `@NotBlank` on the backend — submitting without it fails registration
  with a generic "must not be blank" error tied to no field. Not fixed
  here (backend contract question, not styling); flagging so it doesn't
  get rediscovered.

None of this touches API contracts, routes, or storage keys — pure
CSS/component fixes. `tsc --noEmit`, `vite build` and `vitest run` all
pass; verified live against `spring-boot:run` + real MySQL, not just a
green build.

`frontend/src/components/owner/OwnerLive.tsx`, `frontend/src/styles.css`.

## 2026-09-10 - First-attempt success rate no longer inflated by its own JOIN

Fixing the finding in `docs/audits/2026-09-10-flow-reports-analytics.md`.
`ShipmentRepository.firstAttemptSuccessRaw` computed `COUNT(*)` over
`shipments s LEFT JOIN delivery_attempts da ON da.shipment_id = s.id` — a
shipment with N prior failed attempts joins to N rows, not 1, so the
denominator ("totalDelivered") was silently inflated for any delivered
shipment that had ever failed and been retried. Confirmed live with a
known-ground-truth fixture (3 delivered shipments with 0/1/2 prior
attempts): the endpoint reported 25% instead of the correct 33.3%, and a
direct SQL query isolated the cause to `COUNT(*) = 4` join rows instead of
3 shipments. The bias only ever ran low, never high, and nothing about it
threw an error or otherwise signalled the number was wrong — it would have
kept silently understating delivery performance to any business owner
reading their own reports.

Fixed by replacing the `LEFT JOIN` with a `NOT EXISTS` correlated
subquery, so every shipment contributes exactly one row regardless of its
attempt count. Verified live: the same fixture now reports 33.3%, matching
ground truth. Added
`overview_firstAttemptRate_notInflatedByMultipleAttemptsOnOneShipment` to
`ReportControllerIntegrationTest`. Full backend suite (209 tests) passes.

**Files:** `src/main/java/com/hyperlocal/delivery/repository/ShipmentRepository.java`,
`src/test/java/com/hyperlocal/delivery/controller/ReportControllerIntegrationTest.java`.

## 2026-09-10 - A bad/expired bearer token no longer 401s public endpoints

Fixing the finding in `docs/audits/2026-09-10-flow-public-tracking.md`.
`JwtAuthFilter` ran on every request and short-circuited with a 401 the
instant an `Authorization` header was present and failed to parse or
validate — before Spring Security's own `permitAll()` rules ever got a
chance to run. Confirmed live: `GET /api/track/{token}` (documented as
requiring no authentication at all) returned 200 with no header, but 401
with a garbage or genuinely expired bearer token attached — a real gap for
any caller of the public API that reattaches a stored token unconditionally
(a routine pattern once the 15-minute access-token TTL elapses). The same
gap applied to every other `permitAll()` endpoint (health, swagger, login,
register), not just tracking.

Fixed by extracting the exact `permitAll()` API pattern list out of
`SecurityConfig` into a new `PublicApiPaths` (shared by both
`SecurityConfig.requestMatchers(...)` and `JwtAuthFilter`, so the two lists
cannot drift apart independently). `JwtAuthFilter` now ignores a bad token
on any path matching `PublicApiPaths` — proceeding unauthenticated exactly
as if no header had been sent — while continuing to reject bad tokens with
401 everywhere else. Verified live both ways: `/api/track/{token}` with a
garbage bearer now returns 200; `/api/shipments` (protected) with the same
garbage bearer still correctly returns 401. Full backend suite (208 tests)
passes unchanged.

**Files:** `src/main/java/com/hyperlocal/delivery/security/JwtAuthFilter.java`,
`src/main/java/com/hyperlocal/delivery/security/PublicApiPaths.java` (new),
`src/main/java/com/hyperlocal/delivery/config/SecurityConfig.java`.

## 2026-09-10 - POST /shipments now returns its own auto-assignment event

Fixing the finding in `docs/audits/2026-09-10-flow-shipment-creation.md`.
`ShipmentService.create()` saved the auto-assignment `ShipmentEvent`, then
re-fetched the shipment via `shipmentRepository.findWithDetailById(...)` (an
`@EntityGraph` fetch) to build the response DTO — but the response's
`events` array still came back empty, even though the event was correctly
persisted (visible on any subsequent `GET`). Root cause: `shipment` at that
point is a transient-origin entity (built via `Shipment.builder()`, never
loaded from the DB), so its `events` field is plain `null`, not an
initialized Hibernate collection proxy — and re-querying inside the same
persistence context returns the identical managed Java object unchanged
(JPA's one-object-per-row-per-session guarantee), so the entity-graph fetch
never gets a chance to populate a `null` mappedBy field.

Fixed by setting `shipment.setEvents(List.of(assignEvent))` and
`shipment.setAttempts(Set.of())` directly — both collections' correct
contents were already known (one event just saved, zero attempts on a brand
new shipment) — and removing the now-unnecessary re-fetch entirely.

Checked whether the same bug affects `advance()` (used by
pickup/transit/out-for-delivery/deliver/return) before touching it: it does
not. `advance()` loads its shipment via `shipmentRepository.lockById(...)`,
a genuine DB query, so its `events` field is a real (if uninitialized) lazy
proxy rather than `null`, and the same re-fetch pattern there correctly
reflects a just-added event — confirmed by testing `POST /shipments/{id}/pickup`
directly against a running backend before deciding not to change it.

Re-verified against the real dev backend and MySQL: `POST /shipments` now
returns the auto-assignment event in its own response. Full backend suite
(207 tests) passes.

**Docs updated to match:** `docs/phase-07-shipment-lifecycle/task-05-shipment-service-create.md`
(Step 8, the "Why these lines" entry, the "If it breaks" entries, and the
"What you learned" list).

## 2026-09-10 - Corrected a stale claim about when agent deactivation takes effect

`docs/phase-06-agent-management/task-05-agent-service-deactivate-reactivate.md`'s
"If it breaks" section claimed a deactivated agent's access token "remains
valid for its TTL (typically 15 minutes)" because `JwtAuthFilter` "does NOT
check `isActive` on every request." That was never true against this
codebase's actual security stack: `JwtAuthFilter` calls
`CustomUserDetailsService.loadUserByUsername(email)` on every authenticated
request, which queries `userRepository.findByEmailAndDeletedAtIsNull(email)`

This was already confirmed live during the login-flow audit
(`docs/audits/2026-09-09-flow-login.md` — search for "deactivated agent"):
a deactivated agent's still-unexpired token was rejected on the very next
request. The doc simply hadn't been updated to match; no code changed here,
only the doc's description of existing behavior, plus a second stale
snippet in the same file showing `deleteByUser_Id` as a bare derived method
rather than the explicit-`@Query` form it needs (see the 2026-09-09
"Concurrent password-reset / logout token revocation" entry above for why).

## 2026-09-09 - Concurrent duplicate agent-email creation no longer 500s

Fixing the finding in `docs/audits/2026-09-09-flow-agent-roster-crud.md` —
found via a codebase-wide sweep
(`docs/audits/2026-09-09-sweep-concurrent-write-races.md`) for the same
check-then-write race already fixed three times this session in
`AuthService`. `AgentService.create` checked `userRepository.existsByEmail`
then inserted; two concurrent `POST /agents` calls for the same brand-new
email both passed the check before either wrote, and the loser's
`DataIntegrityViolationException` reached the generic `500` fallback instead
of the same clean `409 DUPLICATE_EMAIL` the sequential case gets.

Fixed with a plain try/catch around `userRepository.save(agent)` — no
isolated-transaction guard needed here, unlike the refresh-token/logout
delete races fixed earlier. This is a single `INSERT` violating a `UNIQUE`
constraint: MySQL/InnoDB doesn't abort the whole transaction on that
failure (only PostgreSQL-style databases do), and Hibernate's `IDENTITY`
generation strategy executes the `INSERT` synchronously inside `save()`, so
the exception surfaces right at the call site with nothing else in the
method depending on the failed, still-transient entity afterward. Confirmed
by testing a plain try/catch here *before* reaching for anything heavier —
it worked on the first attempt, unlike the entity-*delete* races (an
`INSERT` failing and a `DELETE` finding 0 rows are different Hibernate
code paths with different fixes; see the sweep doc for the full comparison).

Re-verified against the real dev backend and MySQL: two concurrent
`POST /agents` calls for the same new email now produce one `201` and one
clean `409` (previously one `201` and one `500`); exactly one `users` row
exists afterward either way. Full backend suite (207 tests) passes.

**Docs updated to match:** `docs/phase-06-agent-management/task-04-agent-service-crud.md`
(the `create` method, and the general lesson about matching the fix to the
failing statement type).

## 2026-09-09 - Concurrent password-reset / logout token revocation no longer 500s

Fixing the finding in `docs/audits/2026-09-09-flow-forgot-password-reset.md`
— the third place this exact bug shape turned up this session.
`RefreshTokenRepository.deleteByUser_Id` (used by `AuthService.logout`,
`AuthService.resetPassword`, and `AgentService.deactivate`) was a Spring Data
*derived* delete method with no `@Query`, which Spring Data implements as
load-the-matching-entities-then-`remove()`-each-one — the same entity-based
delete that expects a row to still be there, already found and fixed for
`deleteByTokenHash` in the login-flow audit. Two concurrent calls that both
try to delete the same user's refresh-token rows (a password reset racing a
logout, two concurrent reset attempts reusing one token, or a deactivation
racing either) hit `ObjectOptimisticLockingFailureException` at commit for
whichever one loses, surfacing as a raw `500` even though the actual outcome
— the tokens are gone — is exactly what was wanted.

Fixed the same way as `deleteByTokenHash`: added an explicit
`@Query("DELETE FROM RefreshToken r WHERE r.user.id = :userId")`, making it a
genuine bulk `DELETE`. Unlike `deleteByTokenHash`, none of the three callers
need to inspect the returned count — deleting zero rows on this path was
never an error condition, the fix just needed the statement to stop
asserting the rows existed.

Re-verified against the real dev backend and MySQL: two concurrent
`/api/auth/reset-password` calls reusing the same token now both return
`204` (previously one `500`); exactly the expected password/token state
holds afterward (last-committed password wins, zero refresh tokens remain).
Normal single-caller `logout` re-verified unaffected. Full backend suite
(207 tests) passes.

**Docs updated to match:** `docs/phase-03-jpa-entities/task-18-create-remaining-repos-and-commit.md`
(the repository method), `docs/phase-06-agent-management/task-05-agent-service-deactivate-reactivate.md`
(the `deactivate` method's own use of this repository method).

## 2026-09-09 - Concurrent refresh-token reuse no longer 500s

Fixing the finding in `docs/audits/2026-09-09-flow-login.md`.
`AuthService.refresh` consumed a refresh token via
`refreshTokenRepository.delete(stored)` — an entity delete that expects the
row to still exist. Two requests racing the exact same (still-valid) refresh
token both pass the lookup and validity checks before either deletes; the
loser's `delete(stored)` then fails at commit with
`ObjectOptimisticLockingFailureException` ("expected row count 1 but was 0"),
surfacing as a raw `500` even though the actual guarantee — only one new
token pair issued — held throughout (the DB confirmed exactly one survivor
after the race).

First fix attempt was to switch to `refreshTokenRepository.deleteByTokenHash(hash)`,
which already existed on the interface — but that method was a Spring Data
*derived* delete (`deleteBy...` with no `@Query`), which Spring Data
implements as load-the-matching-entities-then-`remove()`-each-one internally.
That is the exact same entity-based delete under the hood, so the fix did
nothing on the first attempt (re-verified against the real backend — still a
500 with the identical stack trace). The actual fix was adding an explicit
`@Query("DELETE FROM RefreshToken r WHERE r.tokenHash = :tokenHash")` to
`deleteByTokenHash`, making it a genuine bulk `DELETE` statement that reports
rows-affected (0 or 1) instead of asserting a row was there. `AuthService.refresh`
now checks that count and throws the same `InvalidRefreshTokenException` used
for "token not found" when it's 0 — the loser of the race gets a clean `401`
instead of a `500`.

Re-verified against the real dev backend and MySQL: two concurrent
`/api/auth/refresh` calls reusing the same token now produce one `200` and
one clean `401 INVALID_REFRESH_TOKEN`; exactly one new `refresh_tokens` row
exists afterward either way. Sequential single-use rotation and the
already-expired-token path (which also uses `deleteByTokenHash`) re-verified
unaffected. Full backend suite (207 tests, including two new
`AuthServiceTest` cases pinning this) passes.

**Docs updated to match:** `docs/phase-03-jpa-entities/task-18-create-remaining-repos-and-commit.md`
(the repository method needs an explicit `@Query`, and why

## 2026-09-09 - OTP max-attempts lockout now actually persists; concurrent duplicate registration no longer 500s

Fixing the two backend findings in
`docs/audits/2026-09-09-flow-owner-registration.md`.

**OTP attempt counter (P1).** `OtpService.validateOtp` incremented and saved
`attempt_count` on a wrong code, but ran as plain `@Transactional` — joining
whichever transaction called it. `AuthService.verifyRegistrationOtp` (and
`verifyResetOtp`, same shape) throws a rejection exception in that same method
immediately after a `Failure` result, in the same transaction, so Spring's
default rollback-on-exception undid the increment every time. Six wrong codes
in a row all reported "4 attempts remaining"; the 5-wrong-attempts lockout
never actually tripped, for either registration or password-reset OTPs — no
error, just silent brute-force exposure on a 6-digit code with no other rate
limit on verification attempts. Fixed by changing `validateOtp` to
`@Transactional(propagation = Propagation.REQUIRES_NEW)`, so its writes commit
independently before the caller does anything with the result.

**Concurrent duplicate registration (P2).** Two concurrent requests for the
same new email (either two `/register` calls, or two
`/verify-registration-otp` calls with the same code) both pass their
check-then-write's check before either writes; the DB's `UNIQUE` constraint on
`email` correctly stops the duplicate, but the losing insert threw a raw
`DataIntegrityViolationException` that reached `GlobalExceptionHandler`'s
catch-all as a `500`. A plain try/catch around the insert, still inside the
same request's transaction, does not fix this: Hibernate marks that whole
transaction rollback-only the instant the flush fails, so `AuthService`'s own
transaction ends in `UnexpectedRollbackException` at commit even with the
exception caught. Fixed by moving both risky inserts (the
pending-registration upsert, and the Business+User creation) into a new
`RegistrationRaceGuard` bean, each in its own
`@Transactional(propagation = Propagation.REQUIRES_NEW)` method — a failure
there only rolls back that isolated transaction, so `AuthService` can catch it
cleanly and answer the race with a normal response (a neutral `200` for the
register-race, a clean `409 DUPLICATE_EMAIL` for the verify-race) instead of a
`500`.

Both fixes re-verified against the real dev backend and MySQL (not just unit
tests): 6 wrong codes now correctly lock out at attempt 5
(`otp_records.attempt_count = 5`, `status = INVALIDATED`); two concurrent
`/register` calls for the same email both return clean `200`s; two concurrent
`/verify-registration-otp` calls with the same code produce one `201` and one
clean `409`, with exactly one business/user row in the database either way.
Full backend suite (206 tests) passes.

**Docs updated to match:** `docs/phase-05-auth-and-otp/task-04-otp-service-validate.md`
(the `REQUIRES_NEW` propagation and why), `docs/phase-05-auth-and-otp/task-09-auth-service-register.md`
(new `RegistrationRaceGuard` build step, updated `initiateRegistration`/`createAccount`
listings), `docs/phase-05-auth-and-otp/task-11-auth-service-password-reset.md`
(note that the same fix covers `verifyResetOtp`), `docs/concepts/otp-verification.md`
(the transaction-propagation subtlety). A reader following the guide from
scratch now builds the fixed version directly, not the version this audit
found broken.

## 2026-09-07 - Unreachable backend no longer reports "Internal Server Error"

**Changed:** `frontend/src/lib/apiClient.ts`, `frontend/vite.config.js`.

A registration attempt with Spring Boot not listening showed **"Internal
Server Error"** on the form. Nothing was wrong with the server: Vite's dev
proxy could not open a socket to `localhost:8080`, and `http-proxy`'s default
error path answers the browser with a plain-text `500 Internal Server Error`
of its own. `request()` then fell back to `res.statusText` (every error this
API produces carries a JSON body, so there was nothing else to show), and the
form printed the proxy's invented status. It reads as a backend fault and
sends the reader looking for one.

- **`apiClient.ts` exports `OFFLINE_MESSAGE`** and uses it for the two ways
  the API can be unreachable: a non-JSON `5xx` (something in front of the API
  answered, not the API), and a `fetch` that rejects outright (no proxy in
  front — a built SPA, or a dropped connection). The latter throws
  `ApiError` with **`status: 0`**, which is new: it marks "never reached the
  server" as distinct from any status the API chose. A 5xx *with* a JSON body
  is untouched and still shows the API's own `message`.
- **`OFFLINE_MESSAGE` is deliberately audience-neutral** — "Cannot reach the
  server right now. Check your connection and try again in a moment." A
  deployed shop owner reaches this same branch (Spring Boot serves the built
  SPA same-origin, so there is no proxy, but a gateway 502/503 with an HTML
  body and an offline device both land here), and they can neither restart a
  process nor read a socket error. Two tests in `apiClient.test.ts` assert the
  string names no port, host, `ECONNREFUSED`, proxy or "backend".
- **The dev proxy answers `503` with the error envelope** instead of letting
  http-proxy invent a 500, naming the target and the socket error code
  (`Cannot reach the backend at http://localhost:8080 (ECONNREFUSED). ...`).

Any doc or screenshot showing "Internal Server Error" as a symptom of a
backend-down dev session is now wrong; that path shows the message above.

### The dev-only message cannot reach a deployed user

`vite.config.js` is dev tooling; production runs `java -jar` with the SPA
built into `src/main/resources/static` and served by `SpaFallbackController`,
so the proxy's `BACKEND_UNREACHABLE` body never executes there. Confirmed
against a real `npm run build`: `grep` for `localhost:8080`, `ECONNREFUSED`,
`BACKEND_UNREACHABLE` and `Start the Spring Boot app` finds **0 occurrences**
in `static/assets/*.js`, while `OFFLINE_MESSAGE` is present.

Verified: `npx vitest run` 54/54 (five new cases in `apiClient.test.ts`),
`npx tsc --noEmit` clean, `npx eslint src/` clean, the register form checked
in a browser against a stopped backend (banner reads the proxy's message) and
a running one (`POST /api/auth/register` through the proxy -> 200), and the
production bundle grepped as above.

## 2026-09-05 — Security fixes: plaintext password at rest, register enumeration

### Fix 1: Raw password was stored in `pending_registrations`
**Files changed:** `AuthService.java`, `PendingRegistrationPayload.java` (new), `AuthServiceTest.java`
**Task docs updated:** `phase-05-auth-and-otp/task-08-auth-dtos.md`, `phase-05-auth-and-otp/task-09-auth-service-register.md`
**What changed:** `initiateRegistration` serialized the whole `RegisterRequest`
into `pending_registrations.payload_json`, a plain TEXT column. `RegisterRequest`
carries the plaintext password, so every signup wrote a real password to disk.
The row is not deleted at its 10-minute TTL either — expiry is only checked on
read and `purgeOtpRecords()` runs hourly, so the value could persist ~70 minutes
and indefinitely in a backup taken in that window. The password is now BCrypt
hashed at initiation and carried through a new `PendingRegistrationPayload`
record that holds `passwordHash`, never `password`. `verifyRegistrationOtp`
copies that hash instead of re-encoding. Rows written by the old build
deserialize with a null hash and are reported as `SESSION_EXPIRED` rather than
500; they clear on the next hourly purge.

### Fix 2: `/api/auth/register` disclosed whether an email had an account
**Files changed:** `AuthService.java`, `AuthController.java`, `AuthServiceTest.java`
**Task docs updated:** `phase-05-auth-and-otp/task-09-auth-service-register.md`, `phase-05-auth-and-otp/task-12-auth-controller.md`
**What changed:** a taken address threw `DuplicateEmailException` (409, message
`"Email already in use: <email>"`), so the endpoint could be used to test whether
any given person was registered. It now returns the same 200 and the same

## 2026-09-26 - UI/UX audit fix pass: timestamp contract, three API DTOs gained fields, RegisterRequest gained a required field

Working through `docs/ux-audit/UI-UX-AUDIT.md` (a UI/UX/accessibility audit
run against the live app) surfaced one systemic backend bug and several
contract changes docs should know about.

**Timestamps.** `TimeUtils`'s class doc has always asserted "every
LocalDateTime in this codebase represents a UTC instant", but nothing ever
enforced it — `LocalDateTime.now()` (used throughout `AuthService`,
`AgentInviteService`, `OtpService`, `ShipmentService`, `@CreationTimestamp`/
`@UpdateTimestamp` internally, etc.) returns the *JVM default zone's* wall
clock, not UTC, unless the JVM's default zone genuinely is UTC. On this
machine (and presumably any dev machine whose OS clock is set to local time
rather than UTC) it is not, so every `createdAt`, `deliveredAt`, invite/OTP
expiry and password-changed-at was silently off by the host's UTC offset —
confirmed live: a shipment scheduled for 6 PM IST displayed as 11:30 PM
everywhere (queue, rider app, customer tracking, reports). Fixed by pinning
`TimeZone.setDefault(TimeZone.getTimeZone("UTC"))` as the first line of
`DeliveryApplication.main()`, before Spring/Hibernate load — this makes the
documented invariant actually true instead of coincidentally true only on a
UTC-clocked host. The paired frontend bug (the create-shipment form sent a
zone-less local wall-clock string, which a UTC-pinned backend would now
otherwise mis-parse as a UTC instant) is fixed in
`frontend/src/utils/format.ts` (`localDateTimeToUtcNaive`).

**`RegisterRequest` gained a required field.** `businessPhone` is now
required alongside the existing `phone` — the customer tracking page's Call
button had no number to call because sign-up only ever collected the
owner's personal phone, never the business's. `phone`'s validation pattern
was also unified to match every other phone field in the API
(`[+\d\s\-]{7,20}`, allowing spaces) — it was previously the one field that
rejected the exact placeholder format shown on its own form.
`PendingRegistrationPayload` and `RegistrationRaceGuard.createBusinessAndUser`
carry the new field through to `Business.phone`.

**`AgentSummaryDto` and `AgentResponse` gained `activated`** (true once
`User.passwordChangedAt` is non-null, i.e. the agent has spent an invite).
Drives the owner console's "Invite pending" state — a rider who has never
signed in is no longer indistinguishable from an ordinarily active one.

**`ShipmentSummaryDto` gained `deliveredAt`** (null unless status is
DELIVERED) — the rider app's "Delivered · 7d" stat was computing itself from
`GET /shipments/mine` with no status filter, which per
`ShipmentService.myAssignments`/`NON_TERMINAL_FOR_REASSIGNMENT` never
includes delivered shipments, so the figure was a permanent, silent 0
regardless of how many the rider actually delivered. Fixed by fetching
`status=delivered` separately and filtering that list's `deliveredAt` against
a real 7-day window.

None of phase-01/05/06/07/11's task docs currently show the old 5-field
`RegisterRequest`/`PendingRegistrationPayload`/`AgentSummaryDto`/
`AgentResponse`/`ShipmentSummaryDto` shapes verbatim as of this writing (spot

audit pass over those phases isn't surprised by the extra fields.

760–1119px tablet band, the rider toast covering the sticky action dock,
onboarding-checklist auto-collapse, list sort order, small-sample guards on
report rates, a reports sub-nav for <1050px, favicon/manifest/per-page
document titles, and others) came out of the same audit pass but touch no
